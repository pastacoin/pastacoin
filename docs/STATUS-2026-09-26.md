## 1. What PaSta is

A transactional cryptocurrency designed as a medium of exchange, not a store of value.
Three claims from the whitepaper (PaSta Description.docx, last edited 2025-08-12):

1. **Passive stability.** Average transaction size across the network is the inflation signal.
   Each transaction mints or burns a small amount to push the average back toward target.
   Mint only into above-average transactions, burn only from below-average ones, to blunt self-dealing.
2. **Dynamic chain.** One transaction per block. When no free chain end exists, a node may
   bifurcate; whoever bifurcates must later aggregate. Higher layers have shorter block times.
   Balance blocks checkpoint an address's history.
3. **User-based validation.** No miners. To get your own transaction accepted you first validate
   someone else's (State A -> B), then someone else validates yours (B -> C). Transaction size
   rights scale with how much chain you store (storage proof). Validation tokens scale with size.

Lineage: Covacoco (2017, geographic "cascading zipper" chain + miner incentives for stability)
-> Nano-C (2018, Nano block-lattice + mint/burn during transactions) -> PaSta (2024, current).

Position in the idea portfolio (Aug 2026 ranking): #3 of 20 shelved ideas. Noted strengths:
most intellectually developed non-day-job idea; not fiat-pegged so may sit outside GENIUS/MiCA
stablecoin rules. Noted weakness: brutal cold start, worthless until thousands use it.

## 4. Proposed plan

The whitepaper's value rests on an unproven economic claim (average transaction size is a
usable inflation signal and per-transaction mint/burn can hold purchasing power). That is
testable in simulation for near-zero cost, long before networking or a GUI matter. The plan
therefore front-loads hygiene, then correctness of the single node, then simulation of the
economics and chain shape, then networking.

### Phase 0 — Hygiene (1 session)
- Discard the stale local edits; commit `.gitignore` and `CLAUDE.md`.
- `git rm -r --cached build dist pastacoin.egg-info **/__pycache__`; rebuild artifacts are local only.
- Move master-only tools into `tools/legacy/` on main, then delete `master`.
- Pin dependencies (`requirements.txt` with versions, or `pyproject.toml`), drop `gunicorn` unless Render is revived.
- GitHub Actions: pytest on 3.11 and 3.12 for every push/PR.
- README: replace "conceptual phase" with current status and link this doc.

### Phase 1 — Make the single node honest (2 to 4 sessions)
- One canonical signed payload (sender, receiver, amount, timestamp, nonce). Node rejects unsigned or bad signatures. CLI, wizard and web prototype all sign the same bytes, client side.
- Balance rule: sender must cover `amount - mint`. Single `balance_for` used everywhere, mint-aware.
- Separate B and C: B = my tx embeds proof that I validated a target; C = a *different* address mines my tx. Reject self-validation.
- `verify_chain(chain)` that checks hash links, PoW prefix, balances, and state transitions. Test it against tampered chains.
- Persistence: JSON snapshot on change, load on start (SQLite later).
- Tests for each rule above. Target: every `Node` public method covered.

### Phase 2 — PastaTester: simulate the thesis (4 to 8 sessions, the core work)
- Agent-based economy: N agents, goods with a hidden "real" price level, demand shocks, a hoarder population. Agents transact in PASTA.
- Plug in the stability controller as a pure function `(history) -> mint_or_burn(tx)`. Start with the whitepaper rule (mint into above-average, burn from below-average) and measure purchasing-power drift, variance, and response to shocks.
- Attack models: self-dealing to inflate average, wash trading, sybil validators.
- Chain-shape model: available ends, bifurcation, aggregation debt, layer block times. Measure throughput vs. reorg risk.
- Output: plots + a short results memo that feeds back into the whitepaper. This is what turns the whitepaper from a description into a defended design.

### Phase 3 — Multi-node (after Phase 2 says the design holds)
- Gossip protocol between `Node` instances (start with HTTP peers, then websockets).
- Fork choice / longest-chain rule across layers, mempool sync, block propagation.
- Difficulty retarget that can decrease; size-scaled difficulty and validation counts.
- Storage proof prototype.

### Phase 4 — Public surface
- Redeploy the REST node (Render, Fly, or a small VPS) or make the web prototype run the node in-browser via Pyodide.
- Site refresh: link whitepaper, simulation results, downloadable Pasta Machine build.
- Technical specification document derived from Phases 1 to 3.

### Phase 5 — Perpetual improvement agent
- A remotely reachable agent (chat or Slack style) that answers questions about the project and takes instructions.
- A scheduled run once a day: pull, run tests, read `docs/README.md` and this document, pick the top open GitHub issue in the current phase, implement it with tests, open a PR, append to the changelog, and post a short summary.
- Guard rails: never merges its own PRs without green CI; never edits the whitepaper; stops and asks when an issue is ambiguous.
- Candidate mechanisms: Claude Code scheduled routines (cloud cron) plus a GitHub PR review loop; design to be written in `docs/AGENT.md`.

### Working cadence
- Each session: pull, run tests, pick the top open item, ship a PR with tests, update this doc's changelog.
- Backlog lives as GitHub issues on `pastacoin/pastacoin` labelled by phase.
